1. ¿Qué son los tests de integración?

Un test de integración verifica que varios componentes del sistema funcionan correctamente juntos. A diferencia de un test unitario (que aísla una función y prueba solo esa), un test de integración arranca la aplicación real —o una versión muy cercana a ella— y ejecuta peticiones HTTP contra sus endpoints, comprobando que la respuesta es la esperada.

En este proyecto, los tests de integración:

  • Arrancan la API completa de .NET 10 en memoria (sin necesidad de un servidor externo).
  • Se conectan a una base de datos PostgreSQL real, dedicada exclusivamente a tests (clientmanager_tests).
  • Ejecutan flujos completos: login → cookie de sesión → acceso a recurso protegido → logout.
  • Limpian la base de datos antes de cada test para garantizar independencia entre ellos.
Concepto clave: Los tests de integración comprueban el comportamiento del sistema tal como lo vería un cliente real (un navegador, una app Angular), no solo la lógica interna de una clase.

2. Diferencia entre tipos de tests

Tipo ¿Qué prueba? ¿Usa BD real? Velocidad Herramienta en este proyecto
Unitario Una función o método de forma aislada, con dependencias simuladas (mocks) No Muy rápido (<1ms) No implementado
Integración Varios componentes juntos: controlador + servicio + base de datos + autenticación Sí (BD de tests) Medio (1-5s arranque) xUnit + WebApplicationFactory
Rendimiento (k6) Comportamiento bajo carga: latencia, throughput, errores bajo muchas peticiones simultáneas Sí (servidor real) Lento (minutos) k6
End-to-end (E2E) Flujo completo desde el navegador: UI + API + BD Sí Muy lento No implementado (Cypress / Playwright)

3. Tecnologías utilizadas

3.1 xUnit

xUnit es el framework de testing más utilizado en el ecosistema .NET moderno. Es el recomendado por Microsoft para ASP.NET Core. Permite definir tests con atributos y ejecutarlos mediante dotnet test.

  • Versión usada: xUnit 2.9.3
  • Conceptos clave:
    • [Fact] — marca un método como test individual.
    • IClassFixture<T> — comparte una instancia entre todos los tests de la clase (la factory de la API se crea una sola vez).
    • IAsyncLifetime — permite ejecutar código asíncrono antes (InitializeAsync) y después (DisposeAsync) de cada test.

3.2 Microsoft.AspNetCore.Mvc.Testing

Paquete oficial de Microsoft que permite arrancar la API completa en memoria dentro del proceso del test, sin necesitar un servidor HTTP real. Internamente usa TestServer.

  • Versión usada: 10.0.6
  • Proporciona WebApplicationFactory<TEntryPoint>, que localiza el Program.cs de la API y lo ejecuta en un entorno de test configurable.
  • Permite sobrescribir configuración, servicios y middlewares antes de que la aplicación arranque.

3.3 Respawn

Respawn es una librería especializada en limpiar bases de datos entre tests. En lugar de borrar y recrear la BD completa (lo que sería muy lento), Respawn analiza el esquema y genera un script SQL inteligente que borra solo los datos, respetando las claves foráneas y las tablas que se quieran preservar.

  • Versión usada: 7.0.0
  • Compatible con PostgreSQL mediante DbAdapter.Postgres.
  • Permite excluir tablas del borrado (en nuestro caso: __EFMigrationsHistory y AspNetRoles).

3.4 FluentAssertions

Librería que proporciona una sintaxis de aserciones más legible y expresiva que los métodos estándar de xUnit (Assert.Equal). Las aserciones se leen casi como frases en inglés.

  • Versión usada: 8.9.0
  • Ejemplo: response.StatusCode.Should().Be(HttpStatusCode.OK);
  • En caso de fallo, los mensajes de error son mucho más descriptivos que los de xUnit estándar.

3.5 Npgsql

Driver de PostgreSQL para .NET. Necesario para que Respawn abra una conexión directa a la base de datos y pueda ejecutar el borrado de datos.

  • Versión usada: 10.0.2

3.6 Base de datos de tests

Se creó una base de datos PostgreSQL independiente llamada clientmanager_tests, completamente separada de la base de datos de desarrollo (clientmanager). Esto garantiza que los tests nunca afectan a los datos de desarrollo.

5. Arquitectura del proyecto de tests

El proyecto de tests se compone de tres capas bien diferenciadas:

Archivo Responsabilidad
CustomWebApplicationFactory.cs Arranca la API en memoria. Configura BD de tests, JWT, rate limiter. Se comparte entre todos los tests de una clase.
IntegrationTestBase.cs Clase base que todos los tests heredan. Proporciona el HttpClient listo para usar y limpia la BD antes de cada test.
Tests/AuthTests.cs Los tests concretos del flujo de autenticación.

El flujo de inicialización es el siguiente:

  1. xUnit crea una instancia de CustomWebApplicationFactory (una vez por clase de tests).
  2. CustomWebApplicationFactory.InitializeAsync() aplica migraciones y configura Respawn.
  3. Para cada test individual, xUnit crea una instancia de AuthTests.
  4. El constructor de AuthTests → IntegrationTestBase crea un HttpClient.
  5. IntegrationTestBase.InitializeAsync() llama a ResetDatabaseAsync() → limpia + re-siembra datos.
  6. Se ejecuta el test.
  7. IntegrationTestBase.DisposeAsync() se llama al terminar.

6. Infraestructura: CustomWebApplicationFactory

Archivo: AplicacionAPI/ClientManager.Tests/CustomWebApplicationFactory.cs

Esta clase es el núcleo de la infraestructura de tests. Hereda de WebApplicationFactory<Program> y sobreescribe el comportamiento de la API para adaptarla al entorno de tests.

6.1 Sobreescritura de configuración

La API en producción lee su configuración de appsettings.json y User Secrets (JWT secret, connection string, etc.). En tests, reemplazamos toda esa configuración por valores fijos conocidos:

builder.ConfigureAppConfiguration((ctx, config) =>
{
    config.Sources.Clear();  // elimina appsettings, User Secrets, etc.
    config.AddInMemoryCollection(new Dictionary<string, string?>
    {
        ["ConnectionStrings:DefaultConnection"] = "Host=localhost;Database=clientmanager_tests;...",
        ["Jwt:SecretKey"]         = "TestSecretKey_32CharsMinimumXXXXXX",
        ["Jwt:Issuer"]            = "ClientManagerAPI",
        ["Jwt:Audience"]          = "ClientManagerApp",
        ["SuperAdmin:Email"]      = "admin@clientmanager.local",
        ["SuperAdmin:Password"]   = "TestAdmin@2026!",
        ...
    });
});

6.2 Corrección del JWT (PostConfigure)

Se descubrió un problema sutil: Program.cs captura la clave JWT en una variable local antes de que el callback de ConfigureAppConfiguration corra. Esto significa que la clave de validación de tokens queda con el valor antiguo (de User Secrets), mientras que AuthService sí lee la nueva clave en tiempo de ejecución. El resultado era un mismatch: token firmado con la clave nueva, validado con la clave antigua → 401 Unauthorized.

La solución fue usar PostConfigure<JwtBearerOptions> para sobreescribir la clave de validación después de que Program.cs haya corrido:

services.PostConfigure<JwtBearerOptions>(JwtBearerDefaults.AuthenticationScheme, opts =>
{
    opts.TokenValidationParameters.IssuerSigningKey =
        new SymmetricSecurityKey(
            Encoding.UTF8.GetBytes("TestSecretKey_32CharsMinimumXXXXXX"));
    opts.TokenValidationParameters.ValidIssuer   = "ClientManagerAPI";
    opts.TokenValidationParameters.ValidAudience = "ClientManagerApp";
});

6.3 Desactivación del Rate Limiter

La API tiene un rate limiter configurado: máximo 5 peticiones por minuto por IP en los endpoints /api/auth/*. En el TestServer, todas las peticiones de todos los tests comparten la misma IP (127.0.0.1 o null), por lo que al 6.º login ya se recibe un 429 Too Many Requests.

La solución fue eliminar la configuración original del rate limiter y reemplazarla por una política sin límite (NoLimiter):

services.RemoveAll<IConfigureOptions<RateLimiterOptions>>();
services.Configure<RateLimiterOptions>(options =>
{
    options.AddPolicy("auth", _ => RateLimitPartition.GetNoLimiter("test"));
});

6.4 Inicialización y limpieza con Respawn

Respawn se inicializa una sola vez por clase de tests, analizando el esquema de la BD:

_respawner = await Respawner.CreateAsync(_connection, new RespawnerOptions
{
    DbAdapter        = DbAdapter.Postgres,
    SchemasToInclude = ["public"],
    TablesToIgnore   =
    [
        new Respawn.Graph.Table("__EFMigrationsHistory"),
        new Respawn.Graph.Table("AspNetRoles"),
    ],
});

Antes de cada test individual, se llama a ResetDatabaseAsync(), que:

  1. Ejecuta _respawner.ResetAsync(_connection) — borra todos los datos (excepto las tablas excluidas).
  2. Llama a SeedAsync() — recrea el usuario SuperAdmin con su contraseña, ya que Respawn también borra AspNetUsers.

7. Infraestructura: IntegrationTestBase

Archivo: AplicacionAPI/ClientManager.Tests/IntegrationTestBase.cs

Clase abstracta de la que heredan todos los tests. Su responsabilidad es proporcionar un HttpClient ya configurado y limpiar la BD antes de cada test.

7.1 El problema de las cookies en TestServer

La autenticación del proyecto usa cookies HttpOnly; SameSite=Strict. En un navegador real, las cookies se envían automáticamente en cada petición. En el TestServer in-memory de ASP.NET Core, la opción estándar HandleCookies = true no funciona de forma fiable con cookies SameSite=Strict.

La solución fue implementar un DelegatingHandler personalizado (CookieHandler) que intercepta todas las peticiones HTTP y:

  1. Antes de enviar la petición: añade la cabecera Cookie con todas las cookies acumuladas.
  2. Después de recibir la respuesta: lee las cabeceras Set-Cookie y almacena los valores en un diccionario.
private sealed class CookieHandler : DelegatingHandler
{
    private readonly Dictionary<string, string> _cookies = new();

    protected override async Task<HttpResponseMessage> SendAsync(
        HttpRequestMessage request, CancellationToken cancellationToken)
    {
        // 1. Añadir cookies acumuladas a la petición
        if (_cookies.Count > 0)
        {
            var cookieHeader = string.Join("; ",
                _cookies.Select(c => $"{c.Key}={c.Value}"));
            request.Headers.Remove("Cookie");
            request.Headers.Add("Cookie", cookieHeader);
        }

        var response = await base.SendAsync(request, cancellationToken);

        // 2. Leer y almacenar las cookies de la respuesta
        if (response.Headers.TryGetValues("Set-Cookie", out var setCookies))
        {
            foreach (var raw in setCookies)
            {
                var firstPair = raw.Split(';')[0].Trim();
                var eq = firstPair.IndexOf('=');
                if (eq <= 0) continue;
                _cookies[firstPair[..eq]] = firstPair[(eq + 1)..];
            }
        }

        return response;
    }
}

Este handler se registra al crear el cliente:

Client = factory.CreateDefaultClient(new Uri("http://localhost"), new CookieHandler());

8. Modificaciones al proyecto API

Para que los tests pudieran funcionar fue necesario realizar dos cambios menores en el proyecto ClientManager.API. Ambos son no invasivos y no cambian el comportamiento en producción.

8.1 public partial class Program

En .NET 6+, cuando Program.cs usa top-level statements, la clase Program generada es interna (internal). WebApplicationFactory<Program> necesita poder referenciarla desde el proyecto de tests.

Solución: añadir al final de Program.cs:

app.Run();

// Necesario para que WebApplicationFactory<Program> pueda acceder a esta clase desde el proyecto de tests.
public partial class Program { }

8.2 Cookies Secure condicionales según entorno

Las cookies de acceso y refresco tenían Secure = true hardcodeado. Esto hace que el navegador solo las envíe por HTTPS. En el TestServer (HTTP), las cookies marcadas como Secure no se transmiten, lo que hacía que los tests recibieran siempre 401.

Solución: inyectar IHostEnvironment en AuthController y hacer la flag condicional:

public AuthController(IAuthService authService, IConfiguration configuration, IHostEnvironment env)
{
    _authService  = authService;
    _frontendBaseUrl = configuration["Frontend:BaseUrl"] ?? "http://localhost:4200";
    _isProduction = env.IsProduction();
}

private void SetAccessTokenCookie(string token)
{
    Response.Cookies.Append("accessToken", token, new CookieOptions
    {
        HttpOnly = true,
        Secure   = _isProduction,   // false en Development/Test, true en Production
        SameSite = SameSiteMode.Strict,
        Expires  = DateTimeOffset.UtcNow.AddMinutes(15)
    });
}

9.1 GetCompanies_WithoutAuth_Returns401

¿Qué verifica?

Que el endpoint GET /api/companies devuelve 401 Unauthorized cuando se accede sin ninguna cookie de sesión.

¿Por qué es importante?

Confirma que el middleware de autenticación está activo y que el endpoint está correctamente protegido con [Authorize].

[Fact]
public async Task GetCompanies_WithoutAuth_Returns401()
{
    var response = await Client.GetAsync("/api/companies");
    response.StatusCode.Should().Be(HttpStatusCode.Unauthorized);
}

9.2 Login_WithValidCredentials_Returns200AndNoMfaRequired

¿Qué verifica?

Que el endpoint POST /api/auth/login con credenciales correctas devuelve 200 OK y que el body contiene requiresMfa: false.

¿Por qué es importante?

El SuperAdmin de seed no tiene TOTP activado, por lo que el flujo de login debería emitir tokens directamente sin pedir un segundo factor.

[Fact]
public async Task Login_WithValidCredentials_Returns200AndNoMfaRequired()
{
    var response = await Client.PostAsJsonAsync("/api/auth/login", new
    {
        email    = "admin@clientmanager.local",
        password = "TestAdmin@2026!"
    });

    response.StatusCode.Should().Be(HttpStatusCode.OK);
    var body = await response.Content.ReadFromJsonAsync<JsonElement>();
    body.GetProperty("requiresMfa").GetBoolean().Should().BeFalse();
}

9.3 Login_WithWrongPassword_Returns401

¿Qué verifica?

Que el login con contraseña incorrecta devuelve 401 Unauthorized.

¿Por qué es importante?

Confirma que la validación de credenciales funciona correctamente y que el sistema rechaza contraseñas erróneas.

[Fact]
public async Task Login_WithWrongPassword_Returns401()
{
    var response = await Client.PostAsJsonAsync("/api/auth/login", new
    {
        email    = "admin@clientmanager.local",
        password = "ContraseñaIncorrecta123!"
    });
    response.StatusCode.Should().Be(HttpStatusCode.Unauthorized);
}

9.4 GetCompanies_AfterLogin_Returns200

¿Qué verifica?

Que después de hacer login exitoso, el acceso a GET /api/companies devuelve 200 OK. Es el test más completo porque prueba el flujo de autenticación cookie de principio a fin.

¿Por qué es importante?

Confirma que:

  • El login emite la cookie accessToken correctamente.
  • El CookieHandler la captura y la envía en la siguiente petición.
  • El middleware JWT la lee desde la cookie y valida el token.
  • El endpoint devuelve datos al usuario autenticado.
[Fact]
public async Task GetCompanies_AfterLogin_Returns200()
{
    await LoginAsAdminAsync();
    var response = await Client.GetAsync("/api/companies");
    response.StatusCode.Should().Be(HttpStatusCode.OK);
}

9.5 GetMe_AfterLogin_ReturnsCorrectIdentity

¿Qué verifica?

Que GET /api/auth/me devuelve la identidad correcta del usuario autenticado: email, role=SuperAdmin y totpEnabled=false.

¿Por qué es importante?

Este endpoint es el que usa el frontend Angular al arrancar (APP_INITIALIZER) para recuperar la identidad del usuario desde la cookie. Si falla, el usuario aparece como no autenticado aunque su cookie sea válida.

[Fact]
public async Task GetMe_AfterLogin_ReturnsCorrectIdentity()
{
    await LoginAsAdminAsync();
    var response = await Client.GetAsync("/api/auth/me");

    response.StatusCode.Should().Be(HttpStatusCode.OK);
    var body = await response.Content.ReadFromJsonAsync<JsonElement>();
    body.GetProperty("email").GetString().Should().Be("admin@clientmanager.local");
    body.GetProperty("role").GetString().Should().Be("SuperAdmin");
    body.GetProperty("totpEnabled").GetBoolean().Should().BeFalse();
}

9.6 Refresh_ReturnsNewAccessToken_AndStaysAuthenticated

¿Qué verifica?

Que después de hacer login, llamar a POST /api/auth/refresh devuelve 200 OK y que con el nuevo access token se puede seguir accediendo a recursos protegidos.

¿Por qué es importante?

El access token expira en 15 minutos. El mecanismo de refresh es crítico para que las sesiones largas sigan funcionando sin pedir al usuario que vuelva a hacer login. Este test verifica que el refresh token rota correctamente y que el nuevo access token es válido.

[Fact]
public async Task Refresh_ReturnsNewAccessToken_AndStaysAuthenticated()
{
    await LoginAsAdminAsync();

    var refreshResponse = await Client.PostAsync("/api/auth/refresh", null);
    refreshResponse.StatusCode.Should().Be(HttpStatusCode.OK);

    // Con el nuevo access token en la cookie, la API sigue autenticando al usuario.
    var response = await Client.GetAsync("/api/companies");
    response.StatusCode.Should().Be(HttpStatusCode.OK);
}

9.7 Logout_RevokesSession_Returns401OnNextRequest

¿Qué verifica?

Que después de hacer login y logout, el acceso a GET /api/companies devuelve 401 Unauthorized.

¿Por qué es importante?

El logout debe revocar el refresh token en la BD y eliminar ambas cookies. Si esto no funciona, un usuario que haga logout podría seguir accediendo a recursos protegidos con la cookie anterior (vulnerabilidad de seguridad).

[Fact]
public async Task Logout_RevokesSession_Returns401OnNextRequest()
{
    await LoginAsAdminAsync();

    // Antes del logout el usuario está autenticado.
    var before = await Client.GetAsync("/api/companies");
    before.StatusCode.Should().Be(HttpStatusCode.OK);

    var logoutResponse = await Client.PostAsync("/api/auth/logout", null);
    logoutResponse.StatusCode.Should().Be(HttpStatusCode.NoContent);

    // Tras el logout la cookie queda borrada → 401.
    var after = await Client.GetAsync("/api/companies");
    after.StatusCode.Should().Be(HttpStatusCode.Unauthorized);
}

10. Problemas encontrados y soluciones

# Problema Causa raíz Solución aplicada
1 SuperAdmin no existe al correr el segundo test Respawn borra AspNetUsers entre tests Añadir SeedAsync() que recrea el SuperAdmin después de cada reset
2 Cookies no se envían en la segunda petición (HandleCookies = true no funciona) TestServer in-memory no procesa SameSite=Strict igual que un navegador Implementar CookieHandler : DelegatingHandler que gestiona cookies manualmente
3 Token firmado pero validación falla (401) aunque la cookie llega correctamente Program.cs captura la clave JWT antes de que ConfigureAppConfiguration corra → mismatch de claves PostConfigure<JwtBearerOptions> sobreescribe la clave de validación con el valor de test
4 429 Too Many Requests en el 6.º test Todos los tests comparten IP en TestServer, disparando el rate limiter de /api/auth/* Reemplazar la política "auth" por RateLimitPartition.GetNoLimiter() en el host de tests
5 CI falla con errores de whitespace El código usaba espacios para alinear visualmente los =, que dotnet format no acepta Ejecutar dotnet format y commitear los cambios

12. Integración con CI (GitHub Actions)

El proyecto tiene un workflow de CI configurado en .github/workflows/ci.yml que se ejecuta automáticamente en cada push a master.

12.1 ¿Qué hace el CI?

Job Pasos
Backend (.NET 10) 1. Restaurar dependencias (dotnet restore)
2. Compilar en modo Release (dotnet build --configuration Release)
3. Verificar formato (dotnet format --verify-no-changes)
Frontend (Angular 21) 1. Instalar dependencias (npm ci)
2. Compilar en modo producción (ng build --configuration production)
Nota importante: Los tests de integración xUnit no se ejecutan en el CI actual, porque requieren una base de datos PostgreSQL real. Para ejecutarlos en CI sería necesario añadir un servicio PostgreSQL al workflow (Docker). Esto es una mejora futura posible.

12.2 Notificaciones

GitHub envía un email cuando un workflow falla. Para desactivar las notificaciones de CI: GitHub → Settings → Notifications → Actions → desmarcar Email.

13. Estrategia de ramas Git

Se siguió un flujo de ramas estándar para desarrollar los tests de forma aislada:

Rama Propósito
master Código estable y listo. Nunca se trabaja directamente aquí.
develop Integración de features terminadas. Punto intermedio antes de llegar a master.
feature/integration-tests Rama donde se desarrolló el proyecto de tests. Mergeada a develop cuando estuvo completa.

El flujo de merge fue:

feature/integration-tests → develop → master

Cada merge se hizo con --no-ff (no fast-forward) para preservar la historia de que hubo una rama de feature separada, aunque no sea estrictamente necesario en proyectos individuales.

¿Por qué una rama de feature si trabajamos solos? En equipos, las ramas feature/ permiten que varios desarrolladores trabajen en paralelo sin pisarse. En un proyecto individual, el valor es más formativo: aprender el flujo de trabajo estándar de la industria.
