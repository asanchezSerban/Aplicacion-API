1. Visión general

El frontend de ClientManager es una SPA (Single Page Application) construida con Angular 21. Esto significa que es una sola página HTML que el navegador carga una vez, y a partir de ahí Angular controla toda la navegación sin recargas del servidor.

Funciona así:

  1. El navegador descarga el HTML inicial más los ficheros JavaScript y CSS compilados.
  2. Angular arranca y toma el control. A partir de aquí, al navegar entre páginas, Angular simplemente muestra u oculta componentes — no se hace ninguna petición HTML al servidor.
  3. Los datos (empresas, usuarios, etc.) se obtienen de la API .NET mediante llamadas HTTP en segundo plano.
El frontend vive en AplicacionAPI/ClientManagerWeb/ y se compila con npm run build. El resultado es una carpeta de ficheros estáticos (HTML, JS, CSS) que se sirven desde IIS.

Dos modos de uso según el rol

SuperAdmin

Ve el panel completo con sidebar, listados de empresas y usuarios, formularios de creación/edición, y el panel de detalle. Necesita tener TOTP activo para acceder.

Cliente (Usuario)

Solo ve su página de perfil (/perfil). No tiene acceso a ninguna otra ruta. Si intenta acceder a /empresas, el guard lo redirige a /perfil.

4. Cómo arranca la app

El proceso de arranque sigue este orden exacto:

1. El navegador carga index.html
└─ Muestra el splash screen (logo + spinner CSS puro, sin Angular)

2. El navegador descarga main.js (el bundle de Angular compilado)

3. main.ts ejecuta bootstrapApplication(App, appConfig)
└─ Carga la configuración global (appConfig)
└─ Registra todos los providers: rutas, HTTP, animaciones, interceptor

4. provideAppInitializer ejecuta auth.initializeAuth() ANTES del primer render
└─ Llama a GET /api/auth/me con la cookie de sesión
└─ Si hay sesión activa: guarda email + rol + totpEnabled en memoria
└─ Si no hay sesión: _identity = null

5. Angular renderiza el componente raíz App
└─ El splash desaparece (Angular reemplaza <app-root>)
└─ El router determina qué página mostrar según la URL actual
└─ Los guards ya tienen el estado de identidad correcto (gracias al paso 4)

4.1 main.ts

Fichero más simple del proyecto. Solo tiene una responsabilidad: arrancar Angular.

import 'zone.js';                          // zona de detección de cambios
import { bootstrapApplication } from '@angular/platform-browser';
import { appConfig } from './app/app.config';
import { App } from './app/app';

bootstrapApplication(App, appConfig)
  .catch((err) => console.error(err));    // si Angular falla al arrancar, loguea el error
  • import 'zone.js' — debe ser la primera línea. Zone.js "envuelve" los eventos del navegador (clicks, timeouts, peticiones HTTP) para que Angular sepa cuándo tiene que actualizar la pantalla.
  • bootstrapApplication(App, appConfig) — le dice a Angular: "el componente raíz es App, con esta configuración".

4.2 app.config.ts

Aquí se registra todo lo que la app necesita globalmente. Es el equivalente al antiguo AppModule pero en formato moderno (standalone).

export const appConfig: ApplicationConfig = {
  providers: [
    provideBrowserGlobalErrorListeners(),          // captura errores no manejados del navegador
    provideZoneChangeDetection({ eventCoalescing: true }), // optimización de zone.js
    provideRouter(routes, withRouterConfig({        // activa el sistema de rutas
      onSameUrlNavigation: 'reload'                 // navegar a la misma URL recarga el componente
    })),
    provideHttpClient(withInterceptors([authInterceptor])), // HTTP con el interceptor de auth
    provideAppInitializer(() => inject(AuthService).initializeAuth()) // se ejecuta ANTES del primer render
  ]
};

Por qué es importante cada línea

  • provideRouter — sin esto, Angular no sabe qué componente mostrar para cada URL.
  • onSameUrlNavigation: 'reload' — si navegas dos veces a /empresas, el componente se recarga (comportamiento de un link normal). Sin esto, la segunda navegación no haría nada.
  • provideHttpClient(withInterceptors([authInterceptor])) — registra el cliente HTTP y le añade el interceptor. Todas las peticiones HTTP de la app pasarán por ese interceptor.
  • provideAppInitializer() — sustituto moderno de APP_INITIALIZER (deprecado en Angular 19+). Ejecuta la función antes del primer render. Más conciso: una sola línea en lugar del bloque provide/useFactory/multi.

4.3 provideAppInitializer — hidratación de la identidad

provideAppInitializer() es la forma moderna (Angular 19+) de ejecutar código asíncrono antes de que se renderice cualquier componente. Angular espera a que la función termine antes de mostrar nada. Sustituye al anterior APP_INITIALIZER que requería un bloque más verboso con provide/useFactory/multi.

En este proyecto se usa para resolver el siguiente problema:

Problema sin provideAppInitializer: el usuario recarga la página. Angular arranca, los guards comprueban si está logueado (no, porque aún no se ha cargado nada), lo redirigen al login. Medio segundo después llega la respuesta de /auth/me y resulta que sí estaba logueado. El usuario ve un parpadeo horrible login → panel.
Solución con provideAppInitializer: Angular arranca, espera a que /auth/me responda, guarda la identidad en memoria, y solo entonces renderiza. Los guards ya tienen el estado correcto desde el primer instante. Cero parpadeo. 
// En AuthService:
async initializeAuth(): Promise {
  try {
    const identity = await firstValueFrom(
      this.http.get('/api/auth/me', { withCredentials: true })
    );
    this._identity.set(identity);   // guarda email, rol, totpEnabled en memoria
  } catch {
    this._identity.set(null);       // no hay sesión, o el token expiró
  }
}

5.2 Lazy loading — carga diferida

Todas las páginas se cargan con lazy loading. Esto significa que el JavaScript de cada página no se descarga hasta que el usuario navega a ella.

// En lugar de importar directamente (eagerly):
// import { CompanyListComponent } from './pages/company-list/company-list';

// Se usa loadComponent (lazy):
{
  path: 'empresas',
  loadComponent: () =>
    import('./pages/company-list/company-list').then(m => m.CompanyListComponent),
  canActivate: [authGuard, adminGuard]

Ventaja: el bundle inicial es mucho más pequeño. Un usuario que solo va al login no descarga el código del listado de empresas.

6. Gestión de estado con Signals

6.1 ¿Qué es un Signal?

Un Signal es una variable reactiva de Angular. Cuando su valor cambia, todos los componentes que la usan se actualizan automáticamente en la pantalla.

// Crear un signal
const contador = signal(0);

// Leer su valor (nota los paréntesis — se llama como función)
console.log(contador());    // 0

// Modificar su valor
contador.set(5);            // ahora vale 5
contador.update(v => v + 1); // incrementar: ahora vale 6

// computed: signal derivado de otro signal (solo lectura)
const doble = computed(() => contador() * 2);
console.log(doble());       // 12 — se recalcula solo cuando contador cambia

La diferencia con una variable normal es que Angular "sabe" qué componentes usan cada signal. Cuando el signal cambia, solo esos componentes se re-renderizan — no toda la app.

6.2 AuthService como store de identidad

La identidad del usuario logueado vive en AuthService como un signal privado. Es el único lugar de toda la app donde se guarda quién está logueado.

@Injectable({ providedIn: 'root' })
export class AuthService {
  // Signal privado — solo AuthService puede modificarlo
  private readonly _identity = signal<Identity | null>(null);

  // Signals derivados (computed) — solo lectura desde fuera
  readonly isLoggedIn  = computed(() => this._identity() !== null);
  readonly userEmail   = computed(() => this._identity()?.email   ?? null);
  readonly userRole    = computed(() => this._identity()?.role    ?? null);
  readonly totpEnabled = computed(() => this._identity()?.totpEnabled ?? false);
  readonly clientId    = computed(() => this._identity()?.userId  ?? null);
}

Cualquier componente puede inyectar AuthService y usar estos signals directamente en la plantilla:

// En cualquier componente:
readonly auth = inject(AuthService);

// En la plantilla:
@if (auth.isLoggedIn()) {
  <span>Hola, {{ auth.userEmail() }}</span>
}
Importante: la identidad vive solo en memoria del navegador, no en localStorage ni sessionStorage. Esto es más seguro — si hubiera un XSS, el atacante no puede leer el token ni el rol leyendo el almacenamiento. Al recargar la página, el provideAppInitializer vuelve a llamar a /auth/me para rehidratar.

7. Interceptor HTTP — auth.interceptor.ts

Un interceptor es un middleware de Angular para las peticiones HTTP. Se coloca en el medio entre tu código y el servidor: intercepta cada petición antes de enviarla y cada respuesta antes de que llegue al componente.

El interceptor de este proyecto hace dos cosas:

1. Añadir credenciales a todas las peticiones

Las cookies de sesión (accessToken y refreshToken) son HttpOnly — JavaScript no puede leerlas directamente. Pero el navegador las envía automáticamente si le dices que incluya credenciales:

const reqWithCreds = req.clone({ withCredentials: true });
return next(reqWithCreds);   // envía la petición con las cookies adjuntas

2. Refresh automático cuando el token expira (401)

El access token dura 15 minutos. Cuando expira, el servidor devuelve 401. El interceptor lo captura, renueva el token silenciosamente, y reintenta la petición original — sin que el usuario se entere.

El problema es que pueden llegar varios 401 simultáneos (varias peticiones fallando a la vez). Si todas intentan hacer el refresh, se generan tokens duplicados. La solución es un candado global:

let isRefreshing = false;
const refreshResult$ = new BehaviorSubject<boolean | null>(null);

// Si ya está refrescando, esperar al resultado
if (isRefreshing) {
  return refreshResult$.pipe(
    filter(result => result !== null),  // esperar a que deje de ser null
    take(1),
    switchMap(success => success ? next(reqWithCreds) : throwError(() => error))
  );
}

// Primera petición en fallar: tomar el control del refresh
isRefreshing = true;
refreshResult$.next(null);  // resetear el tablón

return from(authService.refresh()).pipe(
  switchMap(success => {
    isRefreshing = false;
    refreshResult$.next(success);  // notificar a las peticiones en espera
    return success ? next(reqWithCreds) : throwError(() => error);
  })
);

El BehaviorSubject actúa como tablón de anuncios: la primera petición en fallar anuncia "estoy refrescando" (null), y cuando termina anuncia el resultado (true/false). Las demás peticiones esperan escuchando ese tablón.

Qué endpoints están en la lista blanca

Los endpoints de auth no pasan por el mecanismo de refresh (evitar recursión):

  • /auth/login — si falla con 401, es contraseña incorrecta
  • /auth/refresh — si falla, el refresh token expiró → logout
  • /auth/me — si falla en el arranque, es que no hay sesión
  • /auth/mfa-verify, /auth/forgot-password, /auth/reset-password

8. Guards de rutas

Los guards son funciones que Angular ejecuta antes de activar una ruta. Pueden dejar pasar (return true), redirigir (return router.createUrlTree(['/login'])), o bloquear (return false).

8.1 authGuard — ¿estás logueado?

export const authGuard: CanActivateFn = (_route, state) => {
  const authService = inject(AuthService);
  const router      = inject(Router);

  if (authService.isLoggedIn()) return true;  // ✅ dejar pasar

  // ❌ no logueado → ir al login, guardando la URL actual para volver después
  return router.createUrlTree(['/login'], { queryParams: { returnUrl: state.url } });
};

El returnUrl en los query params permite que, tras hacer login, el usuario llegue a la página que intentaba visitar (en lugar del home por defecto).

8.2 adminGuard — ¿eres SuperAdmin con TOTP activo?

export const adminGuard: CanActivateFn = () => {
  const authService = inject(AuthService);
  const router      = inject(Router);

  // 1. ¿Eres SuperAdmin?
  if (authService.userRole() !== ROLES.SUPER_ADMIN)
    return router.createUrlTree(['/perfil']);   // ← Cliente va a su perfil

  // 2. ¿Tienes TOTP configurado?
  if (!authService.totpEnabled())
    return router.createUrlTree(['/configurar-totp']);  // ← forzar configuración

  return true;  // ✅ SuperAdmin con TOTP activo
};

Este guard implementa la regla de negocio: el SuperAdmin no puede acceder al panel de gestión sin haber configurado TOTP. Si hace login pero no lo ha configurado, es redirigido a /configurar-totp automáticamente.

8.3 guestGuard — ¿eres un visitante (no logueado)?

export const guestGuard: CanActivateFn = () => {
  const authService = inject(AuthService);
  const router      = inject(Router);

  if (!authService.isLoggedIn()) return true;  // ✅ no logueado, dejar pasar

  // Ya está logueado → redirigir al home según su rol
  const home = authService.userRole() === ROLES.SUPER_ADMIN ? '/empresas' : '/perfil';
  return router.createUrlTree([home]);
};

Protege las páginas públicas (login, mfa, recuperar-password). Si un usuario ya logueado intenta ir a /login, lo lleva directamente a su página de inicio.

Cómo se combinan los guards en una ruta

canActivate: [authGuard, adminGuard]

// Flujo:
// 1. authGuard: ¿estás logueado?     → NO → /login
//                                    → SÍ ↓
// 2. adminGuard: ¿eres SuperAdmin?   → NO → /perfil
//               ¿tienes TOTP?        → NO → /configurar-totp
//                                    → SÍ → acceso permitido ✅

11. Páginas de autenticación

Estas páginas no tienen sidebar ni navbar. Usan un layout de dos columnas: panel izquierdo con branding (degradado oscuro) y panel derecho con el formulario.

11.1 Login

Fichero: pages/login/login.ts

Formulario de inicio de sesión con email y contraseña. La contraseña tiene un botón para mostrarla/ocultarla.

Flujo al pulsar "Iniciar sesión"

  1. Llama a authService.login({ email, password }).
  2. Si la respuesta tiene requiresMfa: true → navega a /mfa-verificar pasando el email, tipo de MFA ('email' o 'totp') y un posible returnUrl como query params.
  3. Si requiresMfa: false → el servidor ya emitió cookies. Navega a /configurar-totp (si el SuperAdmin no tiene TOTP activo) o al home del rol.

El sessionStorage guarda mfa_otp_expires_at (timestamp de expiración del OTP) para que la siguiente página pueda mostrar el timer de cuenta atrás.

Manejo de errores por código HTTP:

  • 423 — cuenta bloqueada por demasiados intentos.
  • 429 — demasiadas peticiones (rate limiting).
  • Cualquier otro → "Credenciales incorrectas".

11.2 MFA Verificar

Fichero: pages/mfa-verificar/mfa-verificar.ts

Página de verificación del segundo factor. Recibe el tipo de MFA desde los query params de la URL.

Para Email OTP:

  • Muestra 6 cajas de dígito separadas con autoavance (al escribir un dígito, el foco salta a la siguiente caja).
  • Soporte de pegado: si pegas "123456", rellena todas las cajas automáticamente.
  • Navegación con teclado: ArrowLeft/Right para moverse entre cajas, Backspace para borrar y retroceder.
  • Timer de cuenta atrás de 30 segundos (lee el timestamp del sessionStorage).
  • Cuando el timer llega a 0, muestra botón "Volver al login" (el código ha expirado).

Para TOTP:

  • Mismas 6 cajas pero sin timer (los códigos TOTP se regeneran cada 30s automáticamente en la app del móvil).
  • Botón "¿Perdiste el acceso? Usa un código de respaldo" que cambia el modo a un input de texto para el código de 8 caracteres (xxxx-xxxx).

11.3 Configurar TOTP

Fichero: pages/configurar-totp/configurar-totp.ts

Página de configuración del segundo factor para el SuperAdmin. Tiene tres estados:

  1. TOTP inactivo — muestra un botón "Activar autenticación en dos pasos".
  2. Setup en curso — muestra el QR (generado con la librería qrcode), el secreto Base32 para entrada manual, y las 6 cajas para verificar el primer código.
  3. TOTP activo — muestra que está protegido y un botón para desactivarlo.

El QR se genera en el propio navegador a partir del qrUri recibido del servidor: QRCode.toDataURL(data.qrUri) devuelve un data:image/png;base64,... que se asigna al src de un <img>.

11.4 Recuperar contraseña

Fichero: pages/recuperar-password/recuperar-password.ts

Formulario con solo un campo (email). Llama a /auth/forgot-password. Siempre muestra el mismo mensaje de éxito independientemente de si el email existe o no (anti-enumeración).

11.5 Reset contraseña

Formulario para crear una nueva contraseña. Lee el email y el token de los query params de la URL (que llegaron por email). Muestra las reglas de contraseña en tiempo real usando los PASSWORD_RULES de las constantes.

16. Patrones Angular 21 usados en el proyecto

Angular 21 introduce un conjunto de patrones modernos que este proyecto usa de forma consistente. Aquí están explicados:

Standalone components

Antes, los componentes pertenecían a un NgModule. Ahora son independientes (standalone) y declaran sus propias importaciones:

@Component({
  selector: 'app-login',
  standalone: true,          // (implícito en Angular 17+, no hace falta escribirlo)
  imports: [FormsModule, MatButtonModule, RouterLink],  // solo lo que necesita este componente
  template: `...`
})

inject() en lugar de constructor

// Antes (Angular clásico):
constructor(private authService: AuthService, private router: Router) {}

// Ahora (Angular moderno):
private readonly authService = inject(AuthService);
private readonly router      = inject(Router);

Más limpio y permite usar inyección fuera del constructor (en propiedades, funciones).

ChangeDetectionStrategy.OnPush

Por defecto, Angular comprueba si un componente debe re-renderizarse en cada evento del navegador. Con OnPush, solo lo hace cuando cambia un Input, cuando se emite un evento del componente, o cuando un Signal que usa cambia:

@Component({
  changeDetection: ChangeDetectionStrategy.OnPush,
  // ...
})

Con OnPush + Signals, el rendering es mucho más eficiente.

Control flow nativo (@if, @for)

<!-- Antes (directivas estructurales): -->
<div *ngIf="loading">Cargando...</div>
<li *ngFor="let c of companies; trackBy: trackById">{{ c.name }}</li>

<!-- Ahora (control flow nativo): -->
@if (loading()) {
  <div>Cargando...</div>
}
@for (c of companies(); track c.id) {
  <li>{{ c.name }}</li>
}

Más legible, mejor rendimiento y no requiere importar NgIf ni NgFor.

takeUntilDestroyed — evitar memory leaks

Si te suscribes a un Observable en un componente y el componente se destruye sin cancelar la suscripción, hay un memory leak (el Observable sigue ejecutándose en memoria). La solución:

private readonly destroyRef = inject(DestroyRef);

// La suscripción se cancela automáticamente cuando el componente se destruye:
someObservable$.pipe(
  takeUntilDestroyed(this.destroyRef)
).subscribe(...);

toSignal() — convertir Observable a Signal

// Un Observable del router convertido en Signal:
private readonly currentUrl = toSignal(
  this.router.events.pipe(
    filter(e => e instanceof NavigationEnd),
    map(e => e.urlAfterRedirects)
  ),
  { initialValue: this.router.url }
);

// Ahora se puede usar como un signal en la plantilla:
isFullscreen = computed(() => FULLSCREEN_ROUTES.some(p => this.currentUrl().startsWith(p)));

Guards funcionales

// Antes (clase que implementa CanActivate):
@Injectable()
class AuthGuard implements CanActivate {
  canActivate(): boolean { ... }
}

// Ahora (función pura):
export const authGuard: CanActivateFn = (route, state) => {
  const auth = inject(AuthService);
  return auth.isLoggedIn() ? true : router.createUrlTree(['/login']);
};

firstValueFrom() — Observable como Promesa

Los servicios HTTP de Angular devuelven Observable, pero a veces es más cómodo usar async/await. firstValueFrom() convierte un Observable en una Promesa que resuelve con el primer valor:

// En lugar de:
this.http.post('/api/auth/login', dto).subscribe(result => { ... });

// Se puede usar async/await:
const result = await firstValueFrom(
  this.http.post('/api/auth/login', dto)
);

17. Flujos completos de usuario

Flujo 1: SuperAdmin hace login con TOTP

1. Usuario entra a /login
└─ guestGuard: no está logueado → dejar pasar ✅

2. Rellena email + password → pulsa "Iniciar sesión"
└─ LoginComponent.onSubmit()
└─ authService.login({ email, password })
└─ POST /api/auth/login → { requiresMfa: true, mfaType: 'totp', mfaEmail: '...' }

3. LoginComponent navega a /mfa-verificar?email=...&mfaType=totp

4. MfaVerificarComponent.ngOnInit()
└─ Lee email y mfaType de los queryParams
└─ Muestra 6 cajas de dígito

5. Usuario introduce el código de Google Authenticator → pulsa "Verificar"
└─ authService.mfaVerify(email, code)
└─ POST /api/auth/mfa-verify → el servidor emite cookies accessToken + refreshToken
└─ Respuesta: { email, role: 'SuperAdmin', totpEnabled: true }
└─ _identity.set({ email, role, totpEnabled }) — guardado en memoria

6. authService.mfaVerify() navega a /empresas

7. authGuard: isLoggedIn() = true ✅
adminGuard: userRole = 'SuperAdmin' ✅ y totpEnabled = true ✅
→ CompanyListComponent se monta en el router-outlet

Flujo 2: Token expira mientras el usuario trabaja

1. Usuario lleva 15+ minutos en la app
└─ El access token (JWT) ha expirado

2. El usuario hace cualquier acción (buscar empresa, cargar detalle...)
└─ Angular hace GET /api/companies → el servidor devuelve 401

3. auth.interceptor captura el 401
└─ isRefreshing = false → tomar control
└─ isRefreshing = true, refreshResult$.next(null)

4. authService.refresh()
└─ POST /api/auth/refresh (con refreshToken cookie)
└─ El servidor devuelve nuevas cookies accessToken + refreshToken
└─ _identity actualizada

5. interceptor reintenta la petición original
└─ GET /api/companies → 200 OK con los datos
└─ El usuario NO se entera de nada — todo fue transparente

(Si el refresh también falla: _identity = null → el interceptor propaga el error → el componente recibe el error → como isLoggedIn() = false, los guards redirigen a /login en la próxima navegación)

Flujo 3: Cliente hace login con Email OTP

1. LoginComponent → POST /api/auth/login
└─ { requiresMfa: true, mfaType: 'email', mfaEmail: '...', otpExpiresAt: '...' }

2. Login guarda mfa_otp_expires_at en sessionStorage
3. Navega a /mfa-verificar?email=...&mfaType=email

4. MfaVerificarComponent lee la expiración del sessionStorage
└─ Inicia contador regresivo de 30 segundos
└─ Si llega a 0: muestra "Código expirado" + botón "Volver al login"

5. Cliente introduce el código de 6 dígitos del email
└─ POST /api/auth/mfa-verify → cookies emitidas
└─ authService._identity.set({ ..., role: 'Cliente' })

6. authService.mfaVerify() detecta role === 'Cliente'
└─ Navega a /perfil

7. authGuard: isLoggedIn() = true ✅
adminGuard NO está en la ruta /perfil → solo authGuard
→ PerfilComponent.ngOnInit() llama a userService.getMe()
→ Muestra los datos del usuario

Flujo 4: Crear una empresa

1. Admin pulsa "+ Nueva empresa" en /empresas
└─ router.navigate([ROUTES.COMPANY_NEW])

2. CompanyFormComponent.ngOnInit()
└─ route.snapshot.paramMap.get('id') = null → modo "crear"

3. Admin rellena nombre, descripción, estado, email de contacto
└─ Opcionalmente sube un logo (input file → preview)

4. Pulsa "Guardar"
└─ companyService.create(dto)
└─ toFormData(dto) convierte todo a FormData (necesario para el archivo)
└─ POST /api/companies (multipart/form-data)
└─ El backend valida extensión + MIME + magic bytes del logo
└─ Respuesta: Company creada con id

5. notificationService.add({ text: 'Empresa creada', ... })
└─ Guardado en localStorage → aparece en la campana

6. router.navigate([ROUTES.companyDetail(result.id)])
└─ Va a /empresas/42 (por ejemplo)
